# 第十七轮迭代需求：AI 文件安全模型收紧（P1-3）

> 来源：深度测评 `docs/audit-backend-core.md` 的 **P1-3**（AI 文件安全模型边界"形同虚设"）。
> 性质：**安全纵深防御**需求。因 AI 层已拥有 shell 执行权限（`shell_run_command`），本项非"新泄露面"，而是**加固未来无 shell 受限 agent 工具面**的纵深防线。
> 状态：**待产品决策**。已完成的缓解（`fs_copy` 源门，commit `cf85f95`）已封住最具体缺口；本方案评估更高阶收紧的收益/风险。
> 前置：深度测评 P1 批次一/二/三/四已交付，verify 门禁全绿（cargo 398 / clippy / tsc / lint 0 error / vitest 1623 / drift / i18n-scan）。

## 0. 本轮定位

**安全铁律**（`YaMet.md`）：「密钥路径拒绝名单在读写两侧都生效，绝不能被绕过」「在每个边界（IPC、fs、网络、AI 工具面）都做校验」。

当前 AI 文件门禁的架构（均为 **默认放行、source 触发** 模式）：

| 门禁 | 位置 | 触发条件 | 作用 |
|---|---|---|---|
| `enforce_ai_workspace_authorization`（写） | `fs/mod.rs:20` | `source == "ai"` | AI 写目标须在工作区授权根内 |
| `check_read_path_authorized`（读） | `fs/policy.rs:197` | `source == "ai"` | AI 读路径跑敏感清单 + 工作区授权 |
| `check_readable`（敏感清单） | `fs/policy.rs` | `check_read_path_authorized` 内部 | 拒绝 `.env`/`.ssh`/私钥/ADS 等 |
| `WorkspaceRegistry` | `workspace.rs:20` | — | `authorize()` 存根 + `is_authorized()` 前缀匹配 |
| `bootstrap_registry` | `workspace.rs:133` | 启动时 | 无条件 `authorize(launch_dir)` + `authorize(home)` |

**核心问题**（audit-backend-core.md P1-3）：
1. `bootstrap_registry` 无条件授权 home → `is_authorized` 对 home 下任意路径（多数用户的全部可写空间）放行 → **工作区边界对绝大多数用户不构成额外保护**，实际防线只剩敏感清单。
2. `source` 由前端传入且无签名/来源校验 → 任何能 invoke IPC 的代码传 `source: null`/`"editor"` 即整体绕过后端 fs 限制。
3. 代码注释将 AI 门标注为 "authoritative" 言过其实（`fs/mod.rs` 头注释）。

## 1. 基线调研（真实代码）

### 1.1 授权模型
```rust
// workspace.rs:26-36
pub fn authorize(&self, path) -> io::Result<PathBuf> {
    let canonical = std::fs::canonicalize(path)?;
    self.roots.insert(canonical);        // 只存 canonical 根
    Ok(canonical)
}
pub fn is_authorized(&self, target) -> bool {
    self.roots.iter().any(|root| target.starts_with(root))  // 前缀匹配
}
```
`bootstrap_registry`（`workspace.rs:133-138`）：`authorize(launch_dir)` + `authorize(home)`。

### 1.2 source 分布
- **读路径** `check_read_path_authorized`：`source != "ai"` 直接 `Ok(())`（连敏感清单都不跑）→ 正常编辑器/资源管理器读完全无门禁。
- **写路径** `enforce_ai_workspace_authorization`：`source != "ai"` 直接 `Ok(())`。
- `source` 为 `#[tauri::command]` 的 `Option<String>` 参数，由前端 invoke 传入，无后端签名校验。
- 前端调用：编辑器/资源管理器不传 source（=None）；AI 工具层经 `native.ts` 传 `source: "ai"`。

### 1.3 敏感清单（`check_readable`）现状
覆盖较好：`.env*`、`.ssh/*`、私钥/证书（`id_rsa`/`*.pem`/`*.p12`）、NTFS ADS、盘符前缀、verbatim 前缀、尾点尾空格、`comparison_form` 统一剥离。**这部分是扎实的**，且对所有路径生效（在 `check_read_path_authorized` 内、source="ai" 时）。

### 1.4 已完成的缓解
- `fs_copy` 源门（commit `cf85f95`）：AI 源拷贝时目标须工作区授权内 + 源路径跑 `check_read_path_authorized`。封住"任意绝对路径拷入工作区绕过秘密清单"的最具体可被利用缺口。

## 2. 需求项

### P0-1【决策项】是否移除 home 无条件授权？（高风险，默认不改）

**现状**：`bootstrap_registry` 无条件 `authorize(home)`。

**风险**：移除后——
- `user_spawn_cwd_or_home`（`workspace.rs:118`）在 cwd 失效时回退到 home 打开终端 → 若 home 未授权，终端启动 cwd 校验（`authorize_user_spawn_cwd`）会拒绝 → **可能破坏"在 home 打开终端"的常见场景**。
- 用户显式在 home 下打开文件/目录供 AI 处理（AI 写 home 下文件）会被工作区门禁拒绝 → **破坏合法 AI 文件操作**。
- launch dir 若在 home 内（常见），`authorize(launch_dir)` 已覆盖，移除 home 无实际影响；若 launch dir 在 home 外，则 home 下的合法 AI 操作被切断。

**建议**：**保持 home 授权不变**。理由：
1. AI 已有 shell 权限，此门禁是纵深防御（非边界）。
2. 移除的破坏面（home 终端/AI 文件操作）大于收益（对"无 shell 未来 agent"的预加固）。
3. 若要收紧，正确做法是**不预授权 home、改为显式 `workspace_authorize` 时授权**——但这会改变 AI 工具在 home 的默认行为，需用户显式确认。

**备选（若决定收紧）**：仅当 `launch_dir` 在 home 外时才不自动授权 home；或增加"home 内 AI 操作需显式确认"的交互（前端弹窗）——但后者的实现成本高，收益低（AI 本有 shell）。

**验收标准**：默认维持现状（不改 `bootstrap_registry`）；若收紧，须保证 `user_spawn_cwd_or_home` 的 home 回退、用户显式打开的 home 文件 AI 操作均不回归（cargo test 全绿 + 手测"在 home 打开终端/AI 读写 home 文件"）。

### P0-2【建议实施】`source` 来源不可伪造化（低风险，收益中）

**现状**：`source` 是前端可任意传的字符串，`source="ai"` 可由任何 invoke 方伪造，或传 `null` 绕过。

**问题**：当前 AI 有 shell，绕过 fs 门禁无实际危害；但**未来无 shell 的受限 agent 工具面**一旦出现，`source` 伪造就成为实缺口。

**方案（分层，按可落地性排序）**：
1. **方案 A（推荐，最小改动）**：把 `source` 的"ai"判定从"前端字符串"改为"后端权威来源"。由后端在 agent 启动时维护一个 `AiSessionContext`（`Mutex<HashSet<SessionId>>`），AI 工具面发起 fs 命令时**后端**根据调用链标注 source，而非信任前端传参。前端不再传 `source`（或传了也不信）。这是架构级改动，影响所有 fs 命令签名。
   - **改动面**：`fs/*.rs` 所有 `source: Option<String>` 参数 → 后端上下文判定；`native.ts` 前端调用去 source 参数；`WorkspaceRegistry` 增加 agent 会话注册。
   - **风险**：高（波及所有 fs 命令 + 前端 bridge + 测试），需全量回归。
2. **方案 B（中改动）**：保留前端传 source，但后端对 `source=="ai"` 的调用校验一个**后端签发的 agent 令牌**（agent 启动时发 token，AI 工具面 invoke 时附带，后端核对）。前端普通操作不传 token → 无法伪造成 ai。
   - **改动面**：agent 启动发 token、`native.ts` AI 工具面附 token、fs 门禁校验 token。
   - **风险**：中（比 A 小，但仍跨前后端）。
3. **方案 C（最小，仅文档/注释修正）**：暂不改代码，先把 `fs/mod.rs` 头注释从 "authoritative" 改为如实描述"纵深防御层（AI 本有 shell 权限，此层在未来无 shell agent 工具面时提供边界）"，避免误导。风险最低，可立即做。

**建议**：**先做 C（1 行注释，立即）+ 评估 A/B 作为未来迭代项**。A/B 是架构级，收益在当前（AI 有 shell）下不显著，建议纳入专门迭代轮而非安全收紧轮。

**验收标准（C）**：`fs/mod.rs` 头注释改为如实描述；`cargo test` 全绿；无行为变更。

### P1-1【建议实施】补齐 AI 写路径的敏感清单校验（低风险，收益中高）

**现状缺口**：`enforce_ai_workspace_authorization`（写路径）只做工作区授权，**不跑 `check_readable` 敏感清单**。而读路径 `check_read_path_authorized` 会跑。→ AI 写 `~/.bashrc`（若 home 授权则在工作区内）当前不被敏感清单拦截（写=覆盖，风险高于读）。

**方案**：在 `enforce_ai_workspace_authorization` 内，对 `source=="ai"` 的写目标追加 `check_readable(&target.to_string_lossy())` 校验（复用现有敏感清单）。这样 AI 写 `.env`/`.ssh`/私钥等一律拒绝，与读侧对称。

**风险**：低（复用既有函数，逻辑对称）。**注意**：需确认 `enforce_ai_workspace_authorization` 的调用方传的是"解析后绝对路径"，且不影响用户编辑器/资源管理器正常写（那些 source != "ai" 不触发）。

**验收标准**：新增测试——AI 写 `.env`（home 已授权前提下）被拒；用户（source=editor）写 `.env` 不受影响；`cargo test` 全绿。

### P2-1【记录】工作区授权语义文档化

`WorkspaceRegistry.is_authorized` 是前缀匹配（`target.starts_with(root)`），需在注释中明确"子目录/子孙路径均视为已授权"，避免后续误以为只匹配直接子级。
