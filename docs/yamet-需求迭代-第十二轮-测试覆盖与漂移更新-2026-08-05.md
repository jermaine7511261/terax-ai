## 0. 本轮定位（用户命题）

1. **怎么增强测试覆盖率**：前端 107 个测试文件但 coverage 未接入门禁；Rust 429 个测试但 DAP 核心会话零测试。本轮把覆盖率变成「可度量、有门禁、补窟窿」。
2. **定位在漂移更新**：跨轮遗留的「功能已实现但文档停滞」doc debt 本轮集中清偿：YAMET.md 自相矛盾（DAP 命令面新旧并存、全文无 MCP）、两篇英文架构文档、需求汇总滞后两轮、i18n parity 守卫被注释。
3. **技术完成度 8/10、产品成熟度 4/10，主要从产品成熟度下手**：技术地基（PTY/LSP/DAP/MCP/helper）已扎实；产品层面的硬编码英文残留、零空状态面板、无配置引导、无测试保障的新模块是 4/10 的根源。本轮以「成熟度 = 完整性 + 可维护性 + 中文化」收口。
4. **母语简体中文，所有文档、前端以中文为主**：硬编码英文 UI 文案清零、英文架构文档汉化、新增文档一律中文。
5. **DAP、MCP、PTY、LSP 必须原生**（维护者硬约束）：四个协议子系统的**宿主/传输/UI 层必须是 Rust 原生实现**（PTY：`portable-pty` + 原生 helper；LSP/DAP：复用 `lsp/framing.rs` 的 Content-Length 分帧 + 原生子进程宿主；MCP：Rust client/server + 前端原生 store）。禁止引入 tmux、`vscode-debugadapter`/`js-debug` 等外部客户端库、Node/Python 常驻桥接进程。适配器/语言服务器本身是外部二进制是 DAP/LSP 协议的固有设计，不违背原生约束。
6. **Skill、技能沉淀、插件系统也作为原生**（维护者硬约束）：技能（`create_skill` 工具 + `<workspace>/skills/<name>/skill.json` 约定 + 内置扫描）与技能沉淀（agent 长任务后主动调 `create_skill` 把可复用流程固化为技能）由 Yamet 自身实现（前端原生逻辑 + Rust fs 底层 + 安全拒绝名单），禁止外部技能市场/外部运行时。未来插件系统只做**窄范围 AI 工具/片段 bundle**（JSON + 工具白名单，原生解析），若扩展 UI/行为插件必须走 Rust 原生 ABI + 前端原生 store，禁止 VSCode 式扩展宿主、禁止 Node/Python 插件运行时。

### 4.2 新模块测试（前端，函数式核心优先）

原则：**测纯逻辑，不测壳**。每个新模块测试只 import 无 DOM/无 invoke 依赖的部分；invoke 封装用 vi.mock。

| 模块 | 被测对象 | 场景 |
|---|---|---|
| `dap/lib/store.ts` | zustand store 状态机 | create→running→stopped→exited；断点增删；launch 错误态 |
| `dap/lib/breakpointGutter.ts` | 断点 toggle 纯逻辑（若混 DOM 则抽 `toggleBreakpoint(path, line, set)` 纯函数） | toggle 开关、跨文件 map、持久化序列化 |
| `mcp/lib/store.ts` | server 增删/连接状态机/工具列表 | add/remove/list 状态迁移、refresh 后 tools 更新 |
| `source-control` | status 解析、commit 消息组装纯函数 | 脏文件分组、upstream 感知 push 的派生状态 |
| `remote` | 隧道参数组装纯函数 | `-L`/`-R` 参数串生成、host/user 清洗 |
| `search` | 过滤/高亮纯逻辑 | 匹配计数、排序、高亮区间 |
| `gateway/bridge.ts` | 事件类型守卫 | platform-event 的 type 判别 |

每个模块至少 1 个测试文件、覆盖主要状态迁移与错误分支（对齐 docs/contributing/testing.md「测边界、拒绝路径」）。

### 4.3 Rust DAP fake-adapter 测试（第十一轮未落地项，参照 grok 测试支撑工程化）

`dap/session.rs` + `transport.rs` 的测试用**真实子进程 fake 适配器**（不 mock 传输层），方法对齐 grok `xai-grok-test-support` + `pty-harness`（§1.1）：共享测试基建（这里 = fake 适配器脚本 + 分帧 helper）驱动真实进程级协议测试：

```
tests/ 下建 helper：spawn 一个脚本（Unix sh / Windows 由 #[cfg] 分支），
脚本行为：
  1. 读 stdin Content-Length 帧，解出 initialize 请求 → 回 initialize 响应 + initialized 事件
  2. 对 launch 请求 fire-and-forget（延迟响应，验证 launch 不阻塞）
  3. 对任意请求回一个带序列号的响应（验证 id 配对）
  4. 主动发一个 reverse request（runInTerminal）→ 验证 reverse handler 收到
测试断言：
  - dap_session_create 完成 initialize/launch 握手，返回会话 id
  - dap_request_send 的响应与请求 id 一一配对
  - reverse request 经 on_event 通道分发
  - 请求超时（fake 不回 response）→ 30s 内返回超时错误（测试里把超时改小或注入）
  - 适配器崩溃（脚本 exit 1）→ 会话标记 exited + stderr tail 可见
```

接缝：`dap/session.rs` 已是 `pub async fn dap_session_create(config, ...)`，测试直接调用模块函数，不经 tauri。超时时间做成 `DapConfig.timeout_ms` 字段（默认 30000），测试注入 200ms。
