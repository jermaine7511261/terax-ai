## 一、P1 · 微信会话自动重连（功能性升级 · 高优）

**痛点**：微信 iLink 会话不定期过期（`errcode=-14` / `-2` "unknown error"）。当前过期后 poll 暂停 10 分钟，**必须用户手动在设置页重新扫码**，期间 agent 完全失联。

**现状**（源码级）：
- `weixin.rs:571` poll 循环检测 `delay.relogin` → 打日志"manual QR re-login required" → `SESSION_EXPIRED_PAUSE_SECONDS` 暂停。
- `emit_fresh_qr`（:859）生成新 QR 帧，经 `emit(QrLoginFrame::Qr)` 发给前端。
- 前端 `GatewaySection.tsx` 仅在用户点击"连接"时才走 `run_qr_login`。

**升级方案**：
1. **会话过期自动重登（半自动）**：poll 检测 relogin 时，不暂停 10 分钟干等，而是立即：
   - 后台静默调用 `get_bot_qrcode` 拿新 QR → 通过 `platform_event` sink（`set_event_sink` 已接线）推送 `weixin:relogin-qr` 事件到前端。
   - 前端收到后弹出非阻塞 QR 浮层（复用现有 QR 组件），用户扫码即完成重连，无需进设置页。
2. **QR 过期自动刷新**：扫码前 QR 过期（480s deadline）时自动重新获取，无需手动点。
3. **重连成功后恢复 poll**：凭据 `secrets_set` + 更新 adapter token，poll 循环继续（断点续传，`next_sync` 已持久化）。

**验收**：
- [ ] 会话过期后自动推送新 QR 到前端浮层；扫码后 agent 自动恢复，无需进设置页
- [ ] QR 过期自动重取（不需要用户手动刷新）
- [ ] 重连后消息继续收发，无重复/丢失（`message_id` 去重窗口内）

## 二、P2 · 限流后置（功能性升级 · 高优）

**痛点**：`registry.rs` dispatch 循环里，**限流检查（:265）在会话授权检查（:298）之前**。即使微信 DM 已 auto-approve，突发多条消息仍可能因令牌桶耗尽被丢弃（`rate limited`），agent 漏回。

**升级方案**：
1. **限流后置到授权之后**：把令牌桶 `allow()` 检查移到 `authorized` 判定之后。已授权会话（DM auto-trust 或已批准）的消息**不受限流丢弃**，保证 agent 完整接收。
2. **限流仅防未授权滥用**：未授权会话仍走限流，防止陌生群聊轰炸打爆审批队列。
3. **保留去重**：`message_id` 去重仍在最前（防网络重发），与限流分离。

**验收**：
- [ ] 已批准/auto-trust 会话的突发消息全部送达 agent（令牌桶不丢弃授权消息）
- [ ] 未授权会话仍受限流保护
- [ ] `message_id` 去重正常（网络重发不重复处理）

## 三、P3 · 会话授权状态启动恢复（功能性升级 · 高优）

**痛点**：会话授权（`authorized`/`auto_approve`）重启后全部丢失，已批准会话回到"待批准"。凭据已落盘，但**授权白名单写入后从未在启动时恢复**。

**根因（源码级确认）**：
- `session.rs` 已完整实现 `persist()`（:111，原子写 tmp+rename，只存 authorized/auto_approve）和 `load_from()`（:140，读 JSON）。
- 变更点均调 `persist()`（:183/188/223/234/242）——**写入侧完整**。
- **但启动时 `lib.rs:233` 只 `set_persist_path()`，从未调用 `restore`/`load_from`**。`load_from` 仅被测试使用（`session.rs:90` 是测试内联恢复）。
- 结论：`gateway-sessions.json` 会生成且更新，但**启动不读取** → 授权状态丢。

**升级方案**：
1. **新增恢复入口**：在 `GatewayRegistry::new()` 或 `lib.rs` 启动序列，`set_persist_path` 后立即从磁盘 `load_from` 并注入 `SessionRouter`（批准会话标 `authorized`、auto-approve 标 `auto_approve`）。
2. **新增公开方法**：`SessionRouter::restore_from_disk(path)`（或 `load()`），内部调 `load_from` 并 merge 到 `inner`。
3. **DM auto-trust 无需持久化**（扫码即授权，重连后自动重新 approve）；恢复覆盖**手动批准的群聊/其他平台**会话——与 `persist()` 只存 authorized/auto_approve 的语义一致。
4. **补 Rust 单测**：写批准会话 → 新 router `restore_from_disk` → 断言 authorized/auto_approve 恢复、未授权不恢复。

**验收**：
- [ ] 批准一个群聊会话 → 重启应用 → 该会话仍为 authorized，无需重新批准
- [ ] `gateway-sessions.json` 生成并随审批更新（写入侧已存在，回归验证）
- [ ] auto-trust DM 会话不受影响（重连后仍自动授权）

> 注：本项吸收原 P5（`gateway-sessions.json` 落盘核查）。写入侧已完好；真正的 gap 是**启动恢复缺失**。

## 四、P4 · 网关消息独立处理（架构评估 · 单独评审）

**痛点**：微信消息到达后，前端 `App.tsx` bridge 必须开着才触发 `yamet:ai-ask` → composer → LLM。**桌面 App 关闭时，网关消息无人处理、无法回复**。这与"微信自动回复"的核心诉求冲突——用户期望后台也能回。

**现状**：回复链路完全在前端：
- Rust `set_handler` → `yamet:gateway-message` → `App.tsx` bridge → `yamet:ai-ask` → composer → chatRuntime → LLM → `setupGatewayResponseListener` → `gateway_send`。

**升级方向**（架构级，需评估）：
1. **后端持会话上下文并直接调用 LLM**：把回复链路下沉到 Rust——网关收到消息后，后端组装 prompt（含会话历史/系统提示），调 LLM Provider（复用 `modules/agent.rs` 或新后端推理），再 `send_text` 回微信。前端关闭不影响。
2. **后端侧 session 记忆**：Rust 维护每 session 的最近 N 条消息上下文，供独立 LLM 调用。
3. 与 P1/P2/P3 一起，实现"**扫码登录后后台常驻自动回复**"，不依赖桌面 UI 开启。

> ⚠️ 本项改动最大，涉及后端 LLM 推理链路、配置（模型/密钥）在后端的可用性、会话上下文管理。**需用户确认架构取舍后实施**（参照 Hermes `run.py` `_run_agent` 全后端链路）。

**验收**（若实施）：
- [ ] App 关闭时，微信消息仍被 agent 处理并回复
- [ ] 后端会话上下文正确（多轮对话连贯）
- [ ] 模型配置在后端可用（复用现有 Provider/密钥文件）

## 六、P7 · 微信重登 QR 主界面感知（功能性升级 · 高优）

**痛点**：微信会话过期时，后端已推送重登 QR（`yamet:gateway-platform-event`），但**只有设置窗口的 `GatewaySection` 监听了该事件**（`reloginFlow`，:177-215）。用户在主界面（未开设置）时掉线完全无感知，需主动进设置页扫码。

**现状**（源码级）：
- 后端 `emit_fresh_qr`（weixin.rs:859）已通过 platform_event sink 推送 QR 帧。
- `GatewaySection.tsx:177-215` 已实现 `reloginFlow`（监听、显示 QR、扫码后 persist + 自动恢复）——**设置窗口侧完整**。
- `App.tsx` 主界面**无** `yamet:gateway-platform-event` 监听。

**升级方案**：
1. **主界面全局监听**：`App.tsx` 监听 `yamet:gateway-platform-event`，收到 `weixin` QR 帧时弹**全局非阻塞 QR 浮层**（复用 GatewaySection 的 reloginFlow 渲染逻辑，抽成可复用组件 `WeixinReloginOverlay`）。
2. **复用扫码确认**：浮层收到 `confirmed` 帧后调 `gateway_weixin_persist` 持久化新凭据 + 标记完成，自动关闭。
3. **跨窗口一致性**：浮层与设置窗口的 reloginFlow 互斥（或都响应，后端幂等），避免两处同时弹。
4. **带组件测试**：`WeixinReloginOverlay` 渲染 QR/状态/确认/错误分支（jsdom 已就绪）。

**验收**：
- [ ] 主界面会话过期自动弹出重登 QR 浮层；扫码后 agent 自动恢复，无需进设置页
- [ ] QR 过期自动刷新；确认后自动持久化新凭据
- [ ] 与设置窗口 reloginFlow 不冲突；组件测试覆盖渲染/确认/错误

> 注：P7 与 P1（自动重连）协同——P1 保证后端主动推 QR + 自动刷新，P7 保证主界面可见可扫。两者共同实现"微信掉线自动恢复"体验。

## 九·五、P11 · 对话页模型选择器只显示有 key 模型（调研项 · 中优）

**痛点**：对话页顶部模型选择器（`ModelDropdown`，AiStatusBarControls.tsx）在「全部」tab 下显示**所有模型**——包括未配置 API key 的 provider 模型。无 key 模型仅以 `opacity-60` 置灰、点击后跳设置页。用户反馈：**模型选择器应只显示有输入 key 的 LLM 模型**，符合其它类似项目的体验。

**现状**（源码级）：
- `ModelDropdown`（:203-447）：`allModels = [...MODELS, ...epModelInfos]`（:244-247），**不按 key 过滤**。
- `hasKeyFor(id)`（:224-225）：`providerNeedsKey(id) ? !!apiKeys[id] : true`——判断逻辑已有，但只在渲染时用于置灰。
- 点击无 key 模型 → `openSettingsWindow("models")` 跳设置（:432-434）。
- Provider 侧栏已按 configured/unconfigured 分组（:233-242 + :368-383），configured 在前、unconfigured 置灰。
- 已有 `hasKeyForModel()`（chatStore.ts:552）纯函数可复用。

**参考调研（其它项目）**：
- **OpenCode**（E:\Agent\opencode-dev）：模型选择器用 `provider.all` + `connected`——**只显示已连接 provider 的模型**，无 `connected` 的 provider 不出现。用户无需看到"连不上"的模型。
- **Hermes**：配置驱动 allowlist，未配置 provider 不进入模型选择。

**升级方案**（符合「只显示可用模型」体验）：
1. **默认过滤**：「全部」tab 默认只显示**有 key 的模型**（`hasKeyFor(m.provider)` 或 compat/llama.cpp 免 key 恒显示）。无 key 模型不出现。
2. **可切视图**：保留「显示未配置」开关（或 provider 侧栏保留 unconfigured 但点击进配置），满足"想配置但先看"的场景——对齐 opencode 的 connected 概念。
3. **选中模型保护**：若当前 `selectedModelId` 的 key 被移除，模型选择器仍显示当前项并标"需配置 key"，避免静默切换。
4. **免 key 恒显示**：`llama.cpp`（本地）与 custom endpoints（compat）恒显示，不因无 key 隐藏。
5. **带组件测试**：`ModelDropdown.test.tsx`——有 key 显示、无 key 隐藏、切换视图、选中保护。

**验收**：
- [ ] 「全部」tab 只显示有 key / 免 key 模型（grep/组件测试断言）
- [ ] 无 key 模型默认隐藏，但可通过开关/侧栏查看并跳配置
