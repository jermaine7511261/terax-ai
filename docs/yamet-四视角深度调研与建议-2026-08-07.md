## 三、架构师视角

### 3.1 架构评估
**总体**：Tauri 2 标准三件套（Rust 命令层 + webview 前端 + capabilities 权限），在正确的位置做了正确的抽象。

**亮点（架构级）**：
1. **平台抽象层 `@/platform`（265 行 index + 16 个 tauri/ 适配器 + web/ 实现）**——这是全项目最具前瞻性的决策：IPC/事件/存储/路径/OS 全封装，`detectPlatform()` 运行时选择。它同时服务三个目标：测试（mock）、WebUI（远期）、CI 兼容。ROADMAP 的"WebUI"路径已经铺好。
2. **原生铁律**：DAP/MCP/PTY/LSP/SSH/Scheduler 全部 Rust 原生实现（无 Node 桥），前端只是视图。这保证进程生命周期、超时、缓冲全在可信侧。
3. **会话/进程模型**：PTY 托管在 detached helper（TCP loopback + token），主进程重启可 attach——把"终端会话"做成了一等可恢复资源。Windows Job Object + Unix process_group 双轨进程树回收。
4. **状态流干净**：前端 zustand store 每模块独立（8 个 ai store 全带测试），`Live` 接口（chatStore.ts:29-43）把 AI 与终端解耦——AI 不直接摸 PTY，只通过 getCwd/injectIntoActivePty 等窄接口。
5. **安全架构分层**：capabilities（Tauri）→ workspace 授权（Rust）→ 秘密清单 policy（Rust + TS 镜像）→ 前端确认 UI。四层纵深，每层独立可测。

**架构风险点**：
1. **单命令面膨胀**：`lib.rs` 147 个命令。`gateway_*`（19 个）、`git_*`（37 个）、`fs_*`（15 个）三个家族各成体系但都在一个 handler 里。无版本化/分组，WebUI 复用时会撞出接口漂移（已有 check-doc-drift 兜底，但那是文档不是契约）。
2. **前端 24 个模块边界参差**：`ai/`（22 组件 + 8 store + 20+ lib）是事实上的"平台"；`source-control/` 两个 1000+ 行文件；`dap/lsp/mcp` 前端较薄（薄是对的）。
3. **无 E2E 层**：单测覆盖逻辑，但不覆盖"窗口/面板/多模块交互"。
4. **WebUI 目标未定义范围**：memory 说"WebUI 作为原生功能逐步迭代"，但架构上 web/ 后端（IPC 假实现）只有 noop/内存版，缺真正可跑的 web 服务端。

### 3.2 架构师建议（可执行）
- **[P0] 把 `lib.rs` 命令面按域分组为模块级 `invoke_handler` 子表**（或至少在 YAMET.md 增加"命令域分组"表），为 WebUI 契约导出做准备——成本半天，收益是 drift 检查从"存在性"升级为"签名级"。
- **[P1] 定义 WebUI 的 MVP 边界**：写一页 `docs/webui-roadmap.md`，明确 web 版首批能力（终端只读? 编辑器? AI chat?），避免抽象层无限膨胀。现有 `web/` 目录已经是空壳承诺，要么充实要么收敛。
- **[P1] 引入 E2E 冒烟**：`tauri-driver` 或 Playwright WebKit 一条冒烟（启动→开终端→敲命令→出输出），锁住"真机可用"底线。这是当前测试体系最大空洞。
- **[P2] 统一 gateway 三态**：gateway 有 19 个命令 + 5 个 adapter + registry + session 持久化，是本项目复杂度最高的子系统。建议把"配置校验→连接→消息路由→授权"画成一张状态图进 docs，防止第 27 轮迭代时失控。

## 五、后端视角

### 5.1 质量评估
**强（代码级验证）**：
- **`net.rs`**：SSRF 纵深全链（IP 分类含 IPv4-mapped IPv6 特判、DNS 重绑定钉扎、逐跳重定向复核、header 黑名单 + CRLF 拒绝、64MiB 响应上限、流式 chunk 超时）——这是我在同类项目里见过的顶级实现。
- **`fs/policy.rs` + `workspace.rs` + `fs/mutate.rs`**：AI 读写四重门（源标记→秘密清单→受保护目录→workspace 授权），全部 canonical 化后比对；mutate 每个命令都过 `enforce_ai_workspace_authorization`；带 .env/私钥拒绝的集成测试。
- **`gateway/`**：Windows DPAPI 静态加密 + Unix 0700；`TokenBucket` 限流（registry.rs:27）；会话授权默认拒绝 + auto-approve 白名单持久化；微信 iLink 长轮询超时处理严谨（+5s headroom 区分"无消息"与"断连"）。
- **`secrets.rs`**：Linux 0600 + 原子 rename + sync_all + 持锁写（`with_store_mut`）。
- **`proc/job.rs`**：KILL_ON_JOB_CLOSE + terminate()，带真实子进程测试。
- **并发纪律**：全项目 `unwrap_or_else(|e| e.into_inner())` 处理 poisoned lock（有 lock_poison 测试与门禁）；scheduler tick 在锁外做 5 年扫描（mod.rs 注释明确）。

**弱**：
1. **`run_blocking` Windows 窗口期未根治**（见修复验收 #1）——job 创建时机应提前到 spawn 后。
2. **`ai_http_stream` 已修**，但 `ai_http_request` 的 64MiB 上限意味着一个异常 provider 可让单次请求占 64MiB 内存（多并发可叠加）；建议加总内存护栏（如全局 inflight 字节计数）。
3. **`weixin.rs` 1285 行**：单文件过大，adapter 内部有 QR 登录、轮询、消息分类、媒体下载四个子域，可拆 4 文件。
4. **`mcp/client.rs` 649 行 + `transport.rs` 426 行**：MCP 客户端无 TLS 证书固定（走系统根），连接不可信 server 时凭据在 JSON-RPC 里明文——需在 UI 上明示"外部 MCP server 风险"（有审批门禁则 OK）。
5. **`scheduler` 持久化用 `fs::write` 非原子**（`mod.rs` save()）：崩溃可能写坏 scheduler.json；secrets 已经示范了 tmp+rename，应统一。

### 5.2 后端建议（可执行）
- **[P0] `shell/mod.rs` run_blocking：spawn 后立即建 job**：把 `ProcessJob::create_for(child.id())` 从超时分支移到 spawn 成功之后、wait 线程启动之前，job 字段随 child 一起持有到 `wait()` 返回；超时分支只调 `job.terminate()`。删除现有"超时才建"路径。附带收益：正常退出路径也能防孙进程逃逸（job drop 时若进程已退出则无害）。
- **[P1] `scheduler` save() 改原子写**：复用 secrets 的 tmp+rename+sync 模式（`write_store_at` 已有实现，抽公共 util）。
- **[P1] `policy.rs` 正则预编译**：`SECRET_BASENAME_PATTERNS` 改 `static OnceLock<Vec<Regex>>`，热路径省掉每调用编译。
- **[P1] `push_upstream` remote 校验**：复用 `is_remote_name_char`（operations.rs:821），拒绝非法 remote。
- **[P2] `weixin.rs` 拆分子域**：`qr_login.rs` / `poll.rs` / `media.rs` / `messages.rs`。
- **[P2] `ai_http_request` 并发内存护栏**：全局 AtomicUsize inflight bytes，超阈值直接 429。

## 七、一句话结论

工程底子（安全纵深、抽象层、测试纪律、CI 门禁）在同量级项目里是**第一梯队**；当前最大的"假完成"是 Windows 进程树 kill 的窗口期，最大的真风险是**发布物缺席**（一切质量门禁都还没被真实用户验证过），最大的结构性机会是**把平台抽象层兑现成 WebUI**——这三件事按 P0 顺序推进，项目就能从"优秀的私有工程"跨入"可信的开源产品"。
