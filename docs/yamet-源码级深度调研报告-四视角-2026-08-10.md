# yamet 源码级深度调研报告（用户 / 架构师 / 前端 / 后端 四视角）

- 调研对象：`E:/Agent/yamet`（HEAD `4afce4f`，v0.1.26，第二十五轮）
- 规模：Rust ≈ 35.5 万行（17 个模块），TS/TSX ≈ 10 万行（26 个功能模块，707 个文件），212 个前端测试文件 + 592 个 Rust 测试
- 进行中未提交改动：Web 平台 M1（`src/platform/web/server/*` + `scripts/dev-web.mjs`）+ `cli.rs`（`yamet --prompt`）

## 0. 结论速览

**总体：工程成熟度远超同规模个人项目。** 安全纵深（SSRF 防 DNS 重绑定、AI 读写双门、原子写、keyring 密钥）、CI 门禁（audit / lint / tsc / 覆盖阈值 / 体积预算 / 文档漂移）、前端纪律（字段级 zustand selector、事件监听全部带清理、eager 预算锁死）都是教科书级别。**当前唯一的高危敞口集中在未提交的 Web 平台服务端**——它把 Tauri 的命令面用 Node 重写了一遍，但没有复刻任何安全门，且默认绑定所有网卡、无鉴权，合并前必须修复。

**四视角一句话：**
- 用户：功能密度大、空状态/确认/国际化完整；但新 Web 模式是半成品，当前只适合内测。
- 架构师：分层与"AI 全原生"铁律贯彻得好；双平台适配引入语义漂移风险，缺统一契约。
- 前端：性能与代码纪律优秀；体积预算余量仅 2.5%，巨型组件开始逼近维护阈值。
- 后端：安全工程扎实；默认授权 home 目录 + 密钥全量下发前端是仅存的设计级软肋。

## 2. 后端视角（安全 / 正确性 / 资源管理）

### 做得好的（验证过的）
- **SSRF 双保险**：`net.rs` 对 AI 直连路径做"DNS 解析 → 分类 → `resolve_to_addrs` 固定已通过检查的 IP"（`classify_and_collect_safe_ips`），从根上杜绝二次解析重绑定；`web_fetch/ssrf.rs` 覆盖 RFC1918/链路本地/CGNAT/TEST-NET/IPv6 映射等全部私网段，`client.rs` 每次重定向跳都重跑 `check_ssrf`，跨主机重定向直接返回。这是移植 Grok 源码但保留了全部测试（约 60 条）。
- **AI 文件门是双层的**：前端 `security.ts`（第一道）+ 后端 `policy.rs`（权威第二道）：敏感文件名正则（.env/.pem/.key/known_hosts/credentials…）、受保护目录（.ssh/.aws/.kube/.git/etc…）、写路径系统前缀拒绝（/etc//usr/bin//windows/…）、Windows 归一化（NTFS ADS 流、尾点/空格、大小写、UNC 前缀）——测试齐全。
- **原子写与防符号链接**：`write_atomic` 用 `NamedTempFile::new_in(parent)`（O_EXCL 随机名）+ `sync_all` + `persist`；文档写明"随机后缀挡预置符号链接攻击"。
- **AI 会话密钥**：keyring 存储（macOS/Windows），Linux 0600 文件回退；Rust 侧 `secrets::read_key` 直接取用，模型调用走 SSRF 守卫的 `ai_http_stream`，"密钥不经 webview"（除设置页录入时）。
- **进程与资源护栏**：Windows Job Object + `TerminateJobObject` 杀整棵进程树；`ResponseQuotaGuard` 64MiB/会话、256MiB 全局预算；sftp_read 有界读取防 OOM；shell 8 并发信号量；scheduler 锁外扫描已修；`RunEvent::Exit` 显式 kill LSP/MCP/DAP + 关停 pty helper。
- **命令面卫生**：`removeUnusedCommands: true`；`toggle_devtools` 门禁 `debug_assertions`/feature；header 黑名单 + CRLF 注入拦截；git push 上游 remote 名做字符校验。

### 发现的问题
- **[SHOULD] `tauri.conf.json` — asset 协议 scope `**` + CSP `frame-src http: https:` 全放行**
  当前 `assetProtocol.scope = ["**"]` 意味着 webview 可经 `asset://` 读**整块磁盘**；`frame-src 'self' http: https: asset:` 又允许加载任意远程 frame。两者叠加：任何被渲染的远程页面（或未来引入的非沙箱 webview 内容）都有读取本地文件的通道。修复：scope 收窄到 `$APPDATA/**`、`$RESOURCE/**` 等实际需要的目录；`frame-src` 只留 `'self'` + 预览用白名单（如 `http://localhost:* http://127.0.0.1:*`）；`img-src` 保留 `asset:` 即可，`frame-src` 不必放 `asset:`。
- **[SHOULD] `secrets.rs` — `secrets_get_all` 将全部密钥明文下发前端 JS 堆**
  BYOK 的密钥最终都要进前端才能展示/管理，但"全量一次下发"放大了 XSS 单点泄露面（前端若被注入，可一把全提走）。建议改为：`secrets_get_all` 只返回 account 名列表（脱敏尾 4 位），具体值按需 `secrets_get` 单项。
- **[SHOULD] `workspace.rs bootstrap_registry` — 默认授权 home 目录，AI 工作区边界实际等于"全 home"**
  `bootstrap_registry` 无条件 `authorize(home)`，AI 读写门（`check_read_path_authorized`）的"必须落在已授权工作区内"因此在默认配置下退化为只靠敏感文件 denylist。代码注释已承认这是纵深防御而非安全边界（AI 有 shell 权限），可以接受——但建议在 onboarding/设置里向用户**明示**"AI 默认可读写 home 下所有非敏感路径"，并让工作区选择成为一个显式动作而非静默默认。
- **[NIT] `fs` 门的 `source` 是客户端自报字段，无密码学认证**——已有注释承认，属可接受纵深防御；如果未来做"无 shell 受限 agent"，需要把 source 改为 Rust 侧会话绑定，而不是信任前端字符串。
- **[NIT] `lib.rs` 147 个命令全在 `generate_handler!` 单列表**（27KB）——已按域分组注释，可读性尚可；后续若继续膨胀，建议按模块拆 `invoke_handler` 组合。

## 3. 前端视角（性能 / 状态 / 组件）

### 做得好的
- **zustand 纪律满分**：21 个 store 全部模块级，组件全部字段级 selector（`useChatStore((s) => s.mini.open)`），全仓未发现 `useStore()` 无参订阅或对象字面量 selector（这类错误在 zustand v5 会直接导致无限重渲染，代码库完全规避了）。
- **事件监听全部带清理**：抽查 `App.tsx`、`TabBar.tsx`、`AiMiniWindow`、`SurfaceLayer`、`ThemeProvider` 等 12 处 `addEventListener`，无一例外都有对应 `removeEventListener`（TabBar 还处理了 passive:false 的 wheel 劫持）。
- **体积预算纪律**：双入口 lazy 拆分 + `eager-budget.test.ts` 锁死 main/settings 不得急切引入 @codemirror/@uiw/ai/@ai-sdk/streamdown；`size-limit` 门禁在 CI。当前 eager 359/540KB、total 1.56/1.6MB。
- **平台适配层**：`@/platform` 统一抽象（16 接口 × tauri/web 双实现），feature 模块零直接 `@tauri-apps/*` 引用；`detectPlatform()` 启动时一次选择。
- **React 19 + 编译器**：babel-plugin-react-compiler 已接入，healthcheck 进 CI（advisory）。

### 发现的问题
- **[SHOULD] 体积预算余量仅 ~2.5%**：total 1.56MB / 上限 1.6MB。以每轮迭代新增功能的速度，1–2 个功能模块内就会破线。建议：把 size-limit 的 total 上限视为硬约束，同时给 AI 聊天/编辑器这类增长最快的模块做按需分包（已 lazy 的确认无遗漏），并考虑把 `streamdown` 之外的渲染库（markdown 语法高亮）也懒加载。
- **[SHOULD] 巨型组件逼近维护阈值**：`SourceControlPanel.tsx` 62KB / `App.tsx` 55KB / `ModelsSection.tsx` 48KB / `useTabs.ts` 39KB / `useTerminalSession.ts` 37KB / `rendererPool.ts` 34KB。SourceControl 已经有 36KB 的 `useSourceControlPanel.ts` 还是太大。建议：SourceControl/App 按功能区拆 hook + 子面板，单文件 ≤25KB 目标。
- **[NIT] `useShallow` 0 处使用**：目前单字段订阅没问题，但若出现"一次取 3+ 字段"的批量订阅场景（如性能热点面板），v5 没有 useShallow 会重复渲染。属前瞻性提示，不阻塞。
- **[NIT] 21 个 store 无统一持久化 schema/迁移层**：各 store 各自用 plugin-store LazyStore 或 localStorage 持久化，字段增删无版本化。用户数据（会话/记忆/todo/技能状态）跨版本迁移是隐患——建议至少对 AI 会话与记忆类数据引入 `version` 字段 + 迁移函数注册表。
- **未发现**：IPC 竞态（unmount 后 setState）、stale closure、i18n 硬编码（有 AssertSameKeys 双语文案对账 + i18n-scan 门禁）、无 ErrorBoundary（有全局 ErrorBoundary + 各面板空状态）。这些在 CHANGELOG 多轮已闭环。

## 5. 架构师视角（分层 / 演进 / 风险）

### 做得好的
- **"原生铁律"贯彻**：AI 子系统 0.1.26 完成全原生迁移（harness/client/compact/skills/memory/graph/research/computer 全在 Rust），前端降为薄层——与 ROADMAP "AI 为原生一等公民"一致，也消除了 JS 直连第三方 API 的密钥泄露面。
- **进程边界清晰**：主进程（Tauri）/ pty helper（detached，token 鉴权 + 0600 state 文件）/ mcp_server（stdio，只读工作区工具）/ CLI（纯 stdout）四类入口职责分明。
- **可测试性**：命令核心与 Tauri 解耦（`fs_read_file_impl`、`read_store_at`、`should_exit_loop` 等纯函数带测试）；前端纯逻辑抽到 `lib/` leaf 模块（mcpFormat/graphParse/compact 等）。
- **文档对账自动化**：`check-doc-drift.mjs` 校验 YAMET.md 与命令/模块漂移，进 CI。

### 发现的问题
- **[SHOULD] Web 服务端是"第二份命令面"，无共享契约**：`platform/web/server/handlers/*` 用 Node 重写了 fs/git/shell/history 的语义，但没有任何机制保证与 Rust 命令面**行为一致**（本次调研已发现：fs 大小上限不同、无原子写、无 policy、git 只读子集、shell 无进程树杀）。drift 检查只覆盖"Tauri 命令 vs 文档"，不覆盖"web handler vs Tauri 命令"。建议：为共享命令定义契约（zod schema 或 JSON Schema），Rust 与 Node 双侧消费；web handlers 纳入 drift/CI 检查；明确"web 面只读、写操作 Tauri-only"的清单并在运行时强制（当前 `__GIT_WRITE_BLOCKED` 只是声明未执行）。
- **[SHOULD] 双适配器长期成本**：`@/platform` tauri/web 双实现让前端可测，但每个新 Tauri 命令都要决定"web 下要不要做、语义是否一致"，已有 `noop.ts` 静默空实现（如 `pty_close_all` 在 web 下 catch 吞掉）。建议为平台能力建一张"能力矩阵"文档（命令 × tauri/web/行为差异），随 drift 检查。
- **[NIT] CLI 入口（`cli.rs`）尚未纳入 verify/CI 覆盖**：`parse_prompt_args` 是纯函数可测，但目前没有对应测试文件；且 CLI 默认 base_url/model 指向 deepseek 硬编码，产品上应与设置共享 provider 配置。

## 6. 进行中改动专项：Web 平台服务端（合并前必读）

`src/platform/web/server/` 当前状态：`WebSocketServer({ port: 31219 })`，前端 `ws://localhost:31219` 收发 `{id, cmd, args}`。发现的问题按严重度排序：

- **[MUST] 无鉴权 + 默认绑定所有网卡 → 任意网页可驱动式 RCE**
  `new WebSocketServer({ port })` 默认监听 `0.0.0.0`，不校验 Origin、无 token、无 TLS。后果链：用户浏览器打开任意恶意网页 → 该网页 `new WebSocket("ws://localhost:31219")`（浏览器不阻止跨域 WS 连接，只发 Origin）→ 发送 `shell_run_command` → **在用户机器上执行任意命令**（`cwd` 还可任意指定）。若所在网络不拦 31219 端口，同网段其他主机也能直接连。修复（三选一并做）：① `host: "127.0.0.1"` 显式绑定回环；② 握手时校验 `Origin`（仅允许 `http://localhost:*` / `http://127.0.0.1:*` / dev server 端口）；③ 启动时生成随机 token，`dev-web.mjs` 经环境变量注入前端，服务端每个消息校验。
- **[MUST] `handlers/fs.ts` 路径可逃逸 workspace 且无任何 policy**
  `resolve(p) = path.resolve(workspaceRoot, p)`：传绝对路径（`/etc/passwd`、`C:\...`）或 `../` 即逃逸。`fs_read_file`（无敏感文件门，可读 `.env`）、`fs_write_file`（可写任意位置、无大小上限、无原子写）、`fs_delete`（可删任意文件/目录树）、`fs_rename`、`fs_canonicalize` 全部受影响。Rust 侧的 workspace registry + `policy.rs` 在 Node 侧**完全没有对应物**。修复：`resolve()` 加 `path.relative` 包含性校验（拒绝越界），写/删命令至少复刻 `policy.rs` 的敏感文件/目录清单（可先做 basename 级）。
- **[MUST] 注释与实现矛盾：写面被放大**
  `index.ts` 注释"Mutating git/fs writes stay Tauri-only——the web build must not widen the write surface"，但 `fs.ts` 实际注册了 `fs_write_file` / `fs_delete` / `fs_rename`。`git.ts` 的 `__GIT_WRITE_BLOCKED` 是导出常量，没有任何运行时检查引用它。修复：要么删掉写命令注册（遵守注释承诺），要么补上完整安全门后在文档中更新承诺。
- **[SHOULD] `handlers/shell.ts` 超时只杀 shell 不杀进程树**
  `proc.kill("SIGKILL")` 在 Windows `shell: true` 下只终止中间 shell，孙进程会残留；Rust 侧用 Job Object 杀整树，语义不一致。输出用字符串拼接收集（最大 1MB 截断），无背压控制。`cwd` 来自参数未约束在 workspace 内。
- **[SHOULD] `handlers/fs.ts fs_grep` 三个小 bug**
  ① `truncated: false` 硬编码——即使 hits 达到 maxResults 截断也返回 false（与 Rust `fs_grep` 的 `truncated` 语义不一致，前端据此判断"是否还有更多结果"）；② 每行 `content.split("\n")` 在循环里执行两次，大文件 O(n²) 内存抖动；③ 无文件大小上限，可读入 GB 级文件。
- **[SHOULD] `fs_read_file` 256KB 上限 vs Rust 10MB**：web 模式读大文件行为不一致（功能性回退），且 `{ kind: "toolarge" }` 前端 web 适配是否消费该分支需确认。
- **[NIT] `git.ts` `git log -n ${limit}` 模板插值**：limit 未做类型/范围校验（负数会变成 `git log -n -5` 报错）；`git_diff` 忽略入参恒返回 `--stat`。属健壮性小问题，但恰好是 tsc 当前报错的文件，顺手修。
- **[NIT] `ipc.ts` 60s invoke 超时无区分重试**；`__register_channel` 无上限（客户端可无限注册 stream listener 撑爆 Map）——dev 工具可接受，上线前补个 cap。

**修复顺序建议**：鉴权+绑定（MUST-1）→ 路径护栏（MUST-2）→ 写面收敛（MUST-3）→ grep/上限等 SHOULD 一批。全部完成后 `pnpm check-types` 应归零（当前 2 处错误）。
